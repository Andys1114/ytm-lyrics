# YTM 自用歌词插件：设计与验收

> 本页按版本保留早期决策和验收记录；当前范围见 [架构](architecture.md) 与 [使用说明](usage.md)。

## 已确认的范围

- 主要解决很多歌曲完全没有歌词；匹配到自定义歌词时，也优先替换已有原生歌词，不拼接缺失段落。
- 固定自用环境：Android 16 / API 36、root、LSPosed 2.2.1（7912）/ API 102、YTM 9.41.52（94152240）。用户已授权将手机的 9.39.52 保留数据升级到此版本；旧安装包保存在本机 `.device/rollback-9.39.52/`。
- 使用 modern libxposed API 102.0.0，运行时由框架提供，不混入 legacy API。
- 歌词在 YTM 原生歌词页面展示，原生无歌词时也能打开。首版不做悬浮窗、状态栏、逐字或翻译歌词。
- 来源适配器支持启停、排序、按优先级顺序查询。0.1.0 接入 LRCLIB；用户确认后 0.2.0 增加 QQ 音乐，网易云尚未接入。
- 同步歌词优先：前一来源只有可靠纯文本时暂存，继续查后续来源；全部没有可靠同步歌词时使用最高优先级的可靠纯文本。
- 无匹配、来源错误时保留可用原生内容并显示原因，不显示上一首的歌词。
- 不确定匹配由用户选择，保存绑定并允许重选、清除。禁用来源后不使用该来源的绑定。
- 同步随实际播放进度，暂停不推进，跳转后重新定位。切歌后旧请求不得覆盖新歌曲。

## 实现选择

### 匹配与来源

`core` 不依赖 Android 或 Xposed，包含歌曲、候选、LRC、匹配与顺序解析器。自动匹配要求规范化后的歌名、歌手相同、双方时长已知且差不超过 2 秒，并且只有一个可靠候选；不剥除 live/remix 等版本信息。

`app/source` 负责 LRCLIB HTTP 协议和持久化；`LyricsSource` 是新增来源的唯一取词接口。查询发送歌名、歌手、可选专辑、时长，不读取或发送账号凭据。使用超时，404 转候选搜索，429/其他错误显示原因，不循环重试。

手动绑定使用歌曲标识作为键，保存选定候选的完整歌词，位于 YTM 私有 SharedPreferences。它不是通用歌词缓存；清除 YTM 数据会清除设置与绑定。来源排序按稳定 ID 保存，新适配器追加，播放同步和页面不需要跟着改。

### 播放与原生页面

`MediaSession.setMetadata/setPlaybackState` 提供当前歌曲和真实进度；播放时按更新时刻和速度外推，暂停使用固定位置。150 ms 更新可见歌词，时间单位统一为毫秒。请求使用递增代次隔离；迟到的自动查询、人工搜索和选择不能覆盖新歌。

9.41.52 存在两条 UI 路径：旧 `TabbedView` 和设备实际启用的 action-bar / engagement-panel。0.4.1 起，保留原生歌词按钮及面板外壳，在原生呈现入口提供替换正文 View：新版替换 `vke.c()` 的返回值；旧版在 `TabbedView.C(afop, View, View)` 构造不可变 pager 条目前提供替换内容。模块不再作为 LoadingFrameLayout 的同级覆盖层。正文槽互斥挂载自定义显示或完整原生 LoadingFrameLayout；后者保留给原生加载状态及无匹配回退。

无歌词按钮仍可点击，但只产生原生 Snackbar。模块在具体的歌词点击意图之后识别该反馈，通过 `vlf` 注册独立 ID `dev.ytmlyrics.lyrics-panel` 并打开原生 engagement-panel，保留原生标题、关闭、返回与播放器。仅对此独立面板维持原生内容状态，不改变评论或相关推荐。

本机服务器标签为中文，而部分本地资源为英文，因此不能仅比较“没有歌词”的本地字符串。原生 `content_overlay` 由 Elements renderer 管理，历史实测会隐藏或占用输入；0.4.1 的替换正文直接交给原生呈现器，不占用这个 overlay，也不再挪动原生子项的 margin 或屏蔽其无障碍子树。

反射类名、方法和 protobuf 字段均只对 94152240 适配。未适配版本不注入页面；升级 YTM 前需要重新定位并验收。模型由 default instance 新建 builder、copyOnWrite 后设置字段，不修改共享默认实例。

### 验收边界

用户后续实测反馈：手机当前歌曲可以逐行同步，有轻微但可接受的延迟。该曲的逐行同步体验获用户接受，暂不调整统一时间偏移；本次反馈未提供歌名、链接或原生歌词状态，不据此补记《超级敏感》或无原生歌词场景已通过。

已分别验证无原生歌词的页面入口，以及真实网络歌词的渲染、同步、跳转和原生回退。尚未找到 LRCLIB 能成功返回该 A-SOUL MV 歌词的结果，不能据此宣称该曲已补词成功，也不能推断中文曲库覆盖率。

后续复查：按简短歌名“超级敏感”搜索已返回 HTTP 200，含 A-SOUL / 258 秒、另一歌手 / 157 秒两个同步候选；按 A-SOUL / 157 秒精确查询返回 404。原视频为约 157 秒，不能把 258 秒版本或其他歌手的同名歌词当作已验证匹配。下一步应取得准确 YTM 歌曲链接，核对实际演唱版本，再完成无词歌曲的整链路验收；暂不因一次 503 判定来源缺词或立即更换来源。

多源先纯文本后同步、歧义匹配、LRC 时间轴、取消旧请求、来源排序、绑定持久化和禁用来源等由单元测试验证。上述 0.1.0 真机验收时只有一个真实来源。

## 0.2.0：QQ 音乐来源

用户在 GitHub 方案筛选后确认继续实施。适配 `QqMusicSource`，参考 Spotify_lyric 的协议流程，用现有 Java / HttpURLConnection / org.json 实现，不新增 .NET、Kotlin 运行时、服务器或逐字解析器。搜索最多三个歌曲候选，按顺序以数字 `musicid` 取 Base64 LRC；任一候选失败不抹掉其他可用歌词，全无可用结果时保留错误原因。歌曲 ID 使用稳定数字字符串，元数据采用实测的 `albumname`、`interval` 和完整歌手列表。

QQ 默认启用并追加到现有来源次序之后；原先的禁用状态、次序和绑定保留。来源名称在状态和候选选择中显示为“QQ 音乐”。选择来源次序不覆盖已经确认的歌曲绑定。

- PC 生产 Java 代码联网实测：“超级敏感 / A-SOUL”返回 QQ 数字 ID `317199253`、257000 ms、102 个 LRC 时间轴条目，可靠匹配完整版。157000 ms 的短 MV 不自动匹配该完整版或其他歌手的结果。
- 搜索 / 歌词协议、JSONP、Base64、空结果、来源错误、部分候选失败、ID 去重和升级持久化覆盖后，合计 27 个单元测试通过；Lint 零错误，仍有固定 targetSdk 36 的提示；0.2.0 已同签名安装到手机。
- 许可和改编归属位于 `THIRD_PARTY_NOTICES.md` 与 APK `assets/third_party/`。
- 真机更新：0.2.0 已安装并成功加载模块；当前 Through Patches of Violet / Mili 的原生无词按钮能打开独立原生面板。用户随后自行测试新版并反馈“无问题”，该结论记为用户实测反馈，不展开为助手未执行的具体步骤。
- 用户明确要求今后自行完成手机测试，已停止助手的手机验证。之后默认只交付代码、电脑端验证和 APK；ADB 安装、重启、触控及截图等手机操作须另有用户明确授权。项目约定记在根目录 `AGENTS.md`。

## 0.4.1：正文替换与 WebView 限次恢复

按用户确认实现：原生正文与自定义正文互斥挂载，原生模型持有的 LoadingFrameLayout 不销毁，继续接收加载事件；无自定义结果时挂回原对象。崩溃或系统回收 WebView 渲染进程时，先销毁受影响的 WebView，最多自动重建两次（等待 1 秒／3 秒），失败期间继续显示模块逐行歌词。隐藏或拆页取消等待，恢复可见后才继续；ready 不重置预算，手动重试可重置。

实现接缝、状态测试及验收条件见 [0.4.1 实装记录](enhancement-implementation.md#041正文替换与限次恢复)。本次只做电脑检查和 APK 交付，手机挂载、导航及真实进程退出仍由用户验证。

## 0.6.0：封面驱动的 AMLL 背景

用户确认使用 AMLL 自带背景，选择固定依赖中已有的 MeshGradientRenderer，而非另写 CSS 动效。封面独立于歌词候选和同步时间，从宿主媒体会话经缩图后传入本地页；原生歌词标题以同一封面暗色衔接，复用前恢复。背景有自己的静态回退，不消耗 WebView 的两次恢复预算。实现、桌面证据及手机验收要点见 [0.6.0 实装记录](enhancement-implementation.md#060封面驱动的-amll-背景)。
